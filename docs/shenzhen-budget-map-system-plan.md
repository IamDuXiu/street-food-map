## 1. 文档目的

本文档同时承担四项职责：

1. 固化已经对齐的产品目标和 MVP 边界。
2. 给出首版可以直接实现的系统架构、数据模型和接口约定。
3. 将开发拆成可由 AI 逐步完成和验收的任务。
4. 防止开发过程中因临时想法扩大范围或提前建设复杂基础设施。

产品负责人已确认本文档，当前代码已完成到第 16 节阶段 4，并完成阶段 5 的局域网测试准备；真实数据采集和真人测试仍待执行。后续 AI 应从 `README.md`、`docs/PROGRESS.md`、`docs/DECISIONS.md`、`docs/OPERATOR_GUIDE.md` 和 `docs/PHASE5_TEST_GUIDE.md` 获取当前实现与操作状态；任何改变产品边界、数据可信规则或外部服务的决定，必须先更新决策记录。

## 2. 已确认的产品决策

### 2.1 产品目标

帮助用户在 30 秒内回答：

> 我附近哪里有一份单人可购买、日常售价不超过预算、价格信息相对可信的餐食？

产品记录的核心对象不是笼统的“低价餐厅”，而是：

> 某个地点的某份具体餐食，在某个日期被确认售价多少，以及确认依据是什么。

### 2.2 地图范围、首批用户与数据试点

MVP 的**地图导航范围**覆盖整个深圳市，按“城市 → 行政区 → 商圈”组织：深圳市下设福田、罗湖、南山、盐田、宝安、龙岗、龙华、坪山、光明 9 个行政区，并将大鹏新区作为常用区级入口。深汕特别合作区本轮不纳入不连续的深圳城市地图。商圈是产品为了找饭维护的近似范围，不等同于官方行政边界。

地图可浏览不代表已经有数据。首轮真实数据采集和用户测试仍只做两个样板区：

- 学生样板区：深圳大学粤海校区及周边约 1.5 公里。初始 GCJ-02 中心点为 `113.933073, 22.526639`，边界先采用中心点半径，不录入人工多边形。
- 上班族样板区：高新园—科兴科学园—深圳湾科技生态园。初始 GCJ-02 中心点为 `113.945000, 22.540000`，初始矩形范围为西 `113.930`、南 `22.525`、东 `113.960`、北 `22.555`。

两个样板区分别验证大学生和科技园上班族在价格带、使用频率、投稿意愿、导航转化和复访方面的差异。

区域目录暂由代码维护，地图使用地点坐标和 `bbox` 查询，不改动现有 `pilot_zones` 数据模型。`pilot_zones` 继续表示采集/运营试点来源，而不是用户可选的全部地理区域。没有真实数据的行政区或商圈必须显示“待共建”和空状态，禁止用演示点位或外部线索制造覆盖感。

### 2.3 首版形态

- 响应式 Web 应用，优先保证手机浏览器体验。
- 开发期本地运行，完成后提供受控测试地址。
- 暂不开发微信小程序或原生 App。
- 暂不依赖公司主体、认证小程序、自有域名或备案。
- 浏览无需登录。
- 用户可匿名提交线索或纠错，但内容必须审核后才能公开。
- 只有一个后台管理员，即产品负责人。

### 2.4 收录规则

地点至少有一份满足以下条件的餐食，才可进入公开地图：

- 单人可以正常购买，不依赖拼单或多人套餐。
- 日常售价不高于 25 元。
- 不是首单、直播券、限时补贴等临时优惠价。
- 能明确到菜品或套餐名称，而不是只有模糊的人均消费。
- 已经过独立核验并记录核验日期和核验方式。

公开筛选价格档为 15、20、25 元。一个地点必须至少存在一份 25 元以内的有效餐食，才能进入公开地图；公开页面与接口也只展示 25 元以内的餐食。更高价格可作为后台历史事实保留，但不进入 MVP 公开结果。

### 2.5 收录业态

首版可收录：

- 普通餐馆与快餐店
- 商场、园区或街边餐饮档口
- 公众可进入的食堂
- 便利店的固定餐食或套餐
- 有门禁或身份限制的食堂，但必须清楚标记准入条件

首版不收录：

- 流动摊位
- 价格无法稳定确认的临时活动
- 仅依赖团购、优惠券或新客补贴才能达到门槛的餐食
- 只有主观推荐、没有具体餐食和价格的信息

## 3. 数据来源与合规边界

### 3.1 数据供给模型

首版数据分为两层：

1. **外部线索层**：豆瓣帖子、公开网页、用户投稿等提供的待确认信息，只在后台出现。
2. **公开事实层**：经过独立核验后形成的地点、餐食和价格记录，可在公开地图展示。

数据流如下：

```text
人工发现豆瓣等外部线索
        ↓
录入后台“线索池”
        ↓
去重并匹配地点
        ↓
通过线下、电话、商户公开菜单或用户现场证据核验
        ↓
管理员审核
        ↓
生成平台自己的结构化价格记录
        ↓
公开地图展示
```

### 3.2 豆瓣数据使用红线

豆瓣仅作为发现线索的入口，不作为可直接搬运、复制或批量抓取的数据源。

允许：

- 人工查看公开内容并发现可能符合条件的地点。
- 在后台保存来源平台、原始链接和简短的事实性线索摘要。
- 独立核验店名、地址、菜品和价格后，形成平台自己的结构化记录。

禁止：

- 自动化批量抓取豆瓣页面或接口。
- 复制、展示豆瓣帖子、评论、照片、用户名或用户主页信息。
- 将豆瓣帖子本身视为“已核验”依据。
- 暗示产品得到豆瓣授权或与豆瓣存在合作。

后台不得保存不必要的帖子全文。线索摘要只保留核验所必需的店名、疑似菜品、疑似价格和发布时间等事实信息。

### 3.3 允许的核验方式

核验方式按可信程度分为：

| 核验方式 | 代码 | 默认可信等级 | 说明 |
|---|---|---:|---|
| 现场菜单或价签 | `onsite_menu` | 高 | 自己或投稿者近期拍摄 |
| 当次消费小票 | `receipt` | 高 | 需去除个人信息和支付信息 |
| 商户官方公开菜单 | `official_menu` | 中高 | 商户自己的公众号、菜单页或公开价目表 |
| 电话询问 | `phone_check` | 中 | 记录核验日期，不录音、不公开电话号码以外的个人信息 |
| 两名独立用户确认 | `community_confirmed` | 中高 | 两个互不依赖的近期确认 |
| 外部社区帖子 | `external_lead` | 不可公开 | 只能进入线索池 |

### 3.4 图片规则

- 公开图片必须是平台自行拍摄、投稿者明确提交，或有明确使用许可的图片。
- 不复制豆瓣或其他内容平台的图片。
- 上传后转为 WebP、移除 EXIF 等元数据，并限制尺寸与文件大小。
- 小票图片需要遮盖姓名、手机号、支付账号、订单号等不必要信息。
- MVP 不开发在线打码编辑器。投稿者在上传前自行遮挡敏感信息；管理员发现仍含敏感信息时必须将图片设为 `admin_only`，不得公开。
- 管理员可以在本地完成遮挡后，通过后台“上传脱敏替代图”生成新的媒体记录；原图保持 `admin_only`，公开版通过 `replaces_media_id` 关联原图。

## 4. MVP 功能范围

### 4.1 用户端必须实现

1. 地图和餐食列表联动。
2. 读取当前位置；用户拒绝定位时使用试点区默认中心点。
3. 拖动地图后搜索当前视野。
4. 按 15/20/25 元价格上限筛选。
5. 按样板区、餐食类型和客观标签筛选；首版不实现“当前营业”筛选，早餐、夜宵通过标签表达。
6. 按地点名或餐食名进行站内搜索，不调用外部平台的餐馆搜索结果作为公开数据。
7. 查看地点详情、具体餐食、价格、核验时间、核验方式和证据图片。
8. 打开第三方地图进行导航。
9. 匿名提交新地点线索、价格变化、停业或错误信息。
10. 查看收录标准、数据声明和纠错说明。
11. 使用手机浏览器完成所有核心操作。

### 4.2 管理后台必须实现

1. 管理员密码登录和退出。
2. 仪表盘：地点数、有效餐食数、待审核数、待核验线索数、过期价格数。
3. 线索池：新增、编辑、去重、标记核验结果、转为正式记录。
4. 地点管理：新增、编辑、停业、合并重复地点。
5. 餐食与价格管理：新增餐食、登记新价格、标记争议、完成复核或归档。
6. 投稿审核：批准、修改后批准、拒绝，并记录原因。
7. 图片上传、预览、隐私复核和脱敏替代；物理清理由维护策略执行，不在日常后台直接删除审计原图。
8. CSV 批量导入、错误预览和确认导入。
9. 完整数据导出和本地备份。
10. 所有管理动作写入审计记录。

### 4.3 明确不做

- 用户账号、微信登录、关注、私信或评论区
- 点赞排行、贡献积分、勋章和任务系统
- 商户认领、广告、团购、支付和付费排名
- AI 推荐吃什么
- 菜单 OCR 自动入库
- 原生 App 和微信小程序
- 多城市管理平台
- Elasticsearch、Redis、消息队列和微服务
- 自动抓取豆瓣或其他内容平台

### 5.3 移动端交互

- 搜索和筛选位于地图前方，手机端随页面滚动，不遮挡地图操作。
- 地图与结果列表纵向排列，列表是地图信息的完整替代入口。
- 点击地图标记后，同步选中列表中的地点卡片。
- 详情页优先展示最低有效价格、核验时间和导航按钮。
- 不将评分、长评论或营销图片放在首屏。

### 5.4 非技术管理员的核心操作

后台不得要求产品负责人编辑 JSON、SQL 或源代码。

**导入数据：** 登录后台 → 下载 UTF-8 CSV 模板 → 上传 CSV → 查看逐行错误与重复候选 → 返回修改或确认导入 → 查看导入结果。确认导入必须全有或全无，不允许部分成功。CSV 始终不接收证据文件；阶段 3 的证据图片通过独立受控上传链路处理。

**审核投稿：** 打开投稿 → 查看结构化字段、证据和重复候选 → 选择“拒绝”“标记重复”“等待核验”或“核验通过并发布” → 使用对应投稿类型的表单确认正式字段 → 提交。后台不得提供通用 JSON 编辑器。

**更新价格：** 打开地点 → 选择餐食 → 新增一次价格核验 → 填写金额、日期、方式和证据 → 确认发布。系统自动保留旧价格历史。

**备份：** 打开导出页 → 点击生成备份 → 下载一个带时间的 ZIP → 页面显示校验结果。也可使用 `npm run backup`。

**恢复：** 首版出于覆盖风险不在网页提供恢复按钮。产品负责人按操作手册复制一条 `npm run restore` 命令；脚本先校验、再自动备份当前数据，并在最终覆盖前要求输入确认词。

## 6. 核心业务规则

### 6.1 公开价格

一个餐食可以有多条历史价格记录，但公开详情默认展示最新一条状态为 `verified` 的记录。管理员确认一条更新价格时，必须在同一个数据库事务中将上一条当前价格改为 `superseded`。

价格统一以人民币“分”存储，避免浮点误差。页面显示时转换为元。

地点进入并维持公开地图资格的唯一判定谓词为：

```text
place.record_status = active
AND place.business_status IN (open, unknown)
AND 至少存在一个 menu_item.active = 1
AND 该餐食存在当前 status = verified 的价格
AND price_fen <= 2500
AND observed_at 距当前时间 <= 180 天
```

唯一一份 25 元以内的餐食一旦超过 180 天、进入争议、被新价格证明已超过 25 元，或餐食被停用，该地点立即退出公开地图。历史详情只允许管理员查看；重新满足谓词后才恢复公开。

### 6.2 信息新鲜度

- 核验后 0～30 天：近期核验。
- 31～90 天：有效但提示核验日期。
- 91～180 天：显示“可能过期”，仍参与筛选并进入后台复核列表。
- 超过 180 天且没有再次确认：不参与地图点位、最低价和筛选；只在详情的历史记录中显示，并明确提示已过期。

“过期”是查询时计算的展示状态，不由定时任务直接修改原始价格记录。

### 6.3 地点去重

创建地点时执行候选重复检查：

- 规范化名称完全相同，并且两个坐标距离小于 80 米；或
- 标准化地址完全相同。

系统只提示候选重复，不自动合并。名称模糊匹配不属于 MVP，管理员可用名称搜索辅助判断。最终由管理员选择新建、关联已有地点或合并。

### 6.4 匿名投稿

- 所有投稿初始状态为 `pending`。
- 投稿成功不代表公开发布。
- 不要求姓名、手机号或账号。
- 系统生成至少 128 bit 随机查询码，用于查看处理结果；数据库只保存查询码哈希。
- 对公开入口设置频率限制、隐藏蜜罐字段和文件校验。
- 投稿者上传图片前必须确认其有权提交，且同意平台为核验和展示目的使用；管理员可以将图片设为“仅后台”或“允许公开”。

### 6.5 商户信息

商户提交的信息也进入普通审核队列，来源标记为 `merchant_claimed`。管理员认可其具有核验价值时只能将其转为 `needs_verification`，只有完成独立核验后才能批准并生成 `verified` 价格。

### 6.6 投稿批准的事务映射

- `new_place`：创建地点、餐食、首条已核验价格、允许公开的证据和审计记录。
- `new_price`：创建新价格，将上一条当前价格改为 `superseded`，并写审计记录。
- `correction`：通过对应地点/餐食的明确表单修改字段，并写入修改前后摘要；不允许任意 JSON 覆盖。
- `closure`：更新地点营业状态并写审计记录，不删除历史价格。

如果投稿证据不足，管理员只能选择 `needs_verification`。如果正式数据写入、旧价格更新或审计记录任一步失败，整笔批准事务回滚，投稿保持原状态。

### 6.7 投稿类型化契约

`submissions.payload_json` 必须使用 Zod discriminated union，禁止接收任意 JSON。四种类型的公开提交字段如下：

| 类型 | 必填字段 | 可选字段 | 批准动作 |
|---|---|---|---|
| `new_place` | `zoneId`、`placeName`、`address`、`lng`、`lat`、`coordinateSystem=GCJ-02`、`placeCategory`、`menuItemName`、`priceFen`、`observedAt`、`claimedVerificationMethod` | `menuCategory`、`accessType`、`accessNote`、`note` | 创建地点、餐食和首条价格 |
| `new_price` | `placeId`、`menuItemId` 或 `newMenuItemName` 二选一、`priceFen`、`observedAt`、`claimedVerificationMethod` | `note` | 更新已有餐食价格或先创建新餐食 |
| `correction` | `placeId`、`field`、`proposedValue`、`reason` | `menuItemId`；只有修改餐食字段时使用 | 修改白名单字段 |
| `closure` | `placeId`、`closureType`、`observedAt` | `reason` | 标记暂时或永久停业 |

`correction.field` 只允许：`place_name`、`address`、`access_type`、`access_note`、`opening_hours_note`、`menu_item_name`。不允许投稿者通过纠错接口直接改坐标、价格状态、审核状态或来源信息。

`closureType` 只允许 `temporarily_closed`、`closed`。证据图片对所有类型均为可选；没有足够证据的投稿只能进入 `needs_verification`。

### 6.8 地点合并

地点合并必须由管理员明确选择“保留地点”和“重复地点”，并先展示影响预览。确认后在一个事务中：

1. 将重复地点的线索、投稿目标和非冲突餐食关联到保留地点。
2. 若两边餐食的 `normalized_name` 相同，将价格和证据迁移到保留地点对应餐食；不自动删除任何价格历史。
3. 标签取并集，地址、坐标、准入说明和营业状态以管理员在预览页选择的值为准。
4. 重复地点设置为 `record_status=merged` 并写入 `merged_into_place_id`，不物理删除。
5. 写入审计记录；任一步失败则全部回滚。

公开 API 永远排除 `merged` 和 `archived` 地点。MVP 不提供自动拆分合并；误合并需要管理员依据审计记录执行专门的数据修复流程。

## 7. 数据状态机

### 7.1 外部线索

```text
new → triaged → verifying → converted
                 ├→ rejected
                 └→ duplicate
```

### 7.2 匿名投稿

| 当前状态 | 可转状态 | 条件 |
|---|---|---|
| `pending` | `needs_verification` | 线索有价值但证据不足 |
| `pending` | `approved` | 已具备独立核验依据且正式写入事务成功 |
| `pending` | `rejected` / `duplicate` | 无效或重复 |
| `needs_verification` | `approved` | 补充核验完成且正式写入事务成功 |
| `needs_verification` | `rejected` / `duplicate` | 复核后确认无效或重复 |

`approved` 的含义是：核验已经完成，并且在同一事务中成功创建或更新正式数据。管理员认为线索有价值、但证据尚不足时，只能选择 `needs_verification`，不得公开。

### 7.3 价格记录

| 当前状态 | 可转状态 | 条件 |
|---|---|---|
| `pending` | `verified` / `archived` | 核验通过或候选作废 |
| `verified` | `disputed` / `superseded` / `archived` | 收到可信纠错、被新价格替代或确认错误 |
| `disputed` | `verified` / `superseded` / `archived` | 复核后恢复、被新价格替代或作废 |
| `superseded` | 无 | 终态，保留历史 |
| `archived` | 无 | 终态，仅供审计 |

- `pending`：后台候选价格，不公开。
- `verified`：完成核验且可公开。
- `disputed`：收到可信纠错后暂时从公开结果隐藏，等待复核。
- `superseded`：已有更新的已核验价格，只作为历史保存。
- `archived`：错误、无效或不应继续使用的记录，只在审计范围内保留。

只有管理员可以改变价格状态。任何 `verified` 写入、旧价格 `superseded` 更新和审计记录必须属于同一个数据库事务。

`stale` 不作为数据库中的人工状态，而是根据 `observed_at` 动态计算，避免状态与日期不一致。

只记录受控测试需要的最小化事件：事件名、浏览器标签页级随机会话 ID、地点 ID（如适用）、粗粒度参数 JSON 和时间。会话 ID 保存在 `sessionStorage`，关闭标签页后失效；不记录账号、完整 IP 或精确定位。原始事件保留 30 天，之后只保留按天汇总数据。

### 8.11 数据库约束与事务

- SQLite 必须启用外键、WAL 模式和合理的 busy timeout。
- 业务数据采用状态或 `active` 字段归档，不直接级联删除地点、餐食和价格历史。
- 地点合并、投稿批准、价格替换、CSV 确认导入必须使用数据库事务；任一步失败时整体回滚。
- 外键默认 `ON DELETE RESTRICT`。只有尚未被正式价格记录引用的临时图片，或仅关联已拒绝/废弃投稿且达到保留期限的图片，允许由维护事务物理删除。
- 数据库迁移必须可重复检测当前版本，禁止应用启动时静默破坏性改表。

## 9. 查询与排序

### 9.1 地图视野查询

客户端发送当前视野边界：`west,south,east,north`，服务端通过经纬度范围查询地点。

首版数据量预计低于 10,000 个地点，不需要 PostGIS。SQLite 使用 `lng`、`lat` 索引和矩形范围查询即可。查询结果最多返回 500 个地点；超过时提示用户缩小地图或增加筛选条件。

### 9.2 地点最低价

地图卡片中的最低价只计算：

- 地点营业状态为 `open` 或 `unknown`；
- 餐食为 active；
- 价格状态为 `verified`；
- 核验时间未超过 180 天；
- 符合当前价格和标签筛选。

### 9.3 排序

默认列表排序综合考虑：

1. 是否命中当前筛选。
2. 与地图中心或用户位置的距离。
3. 价格信息新鲜度。
4. 最低有效价格。

不使用不可解释的推荐算法。服务端支持“距离最近”“价格最低”“最近核验”三种稳定排序，按主字段、核验日期、地点名称、地点 ID 依次处理相同值。当前用户界面在“我的附近”时按距离排序，其他区域默认按价格排序；首页已提供手动排序下拉（最低价 / 最近核验 / 附近优先，附近仅在定位后可选），并把选择随查询参数下发给 `/api/v1/map?sort=`。该控件已纳入阶段 5 任务测试评估，是否保留以首轮测试结果为准（决策见 `DECISIONS.md` 2026-09-09）。

## 10. API 设计

统一前缀 `/api/v1`，输入输出均使用 JSON；上传图片除外。所有写入接口使用服务端 schema 校验。

### 10.1 公开接口

| 方法与路径 | 用途 |
|---|---|
| `GET /api/v1/map` | 按 bbox、关键词、价格、标签、样板区查询地图点位 |
| `GET /api/v1/recent` | 查询最近核验的公开地点（首页「最近核验」入口） |
| `GET /api/v1/places/:id` | 获取地点、餐食和价格详情 |
| `GET /api/v1/config` | 获取价格档、标签和试点区配置 |
| `POST /api/v1/submissions` | 提交匿名线索或纠错 |
| `POST /api/v1/submissions/:id/media` | 上传投稿证据 |
| `GET /api/v1/submissions/status` | 使用查询码查询审核状态 |

`GET /api/v1/map` 示例参数：

```text
?bbox=113.90,22.50,113.98,22.58
&maxPriceFen=2500
&zoneId=...
&tags=breakfast,meat_and_veg
&sort=distance
```

地图接口只返回卡片所需的精简字段，不返回来源链接、审核备注或全部历史数据。

`GET /api/v1/recent` 示例参数：

```text
?days=7      # 滚动窗口天数，1–30，默认 7
&limit=3     # 返回条数，1–20，默认 5
```

返回结构与 `/api/v1/map` 条目一致：`{ "data": PublicPlace[], "meta": { "count", "days", "limit" } }`。超出参数范围统一返回 400。

公开地点 DTO 的餐食条目除既有字段外新增：`freshness`（近期核验/有效/可能过期/已过期 四档）、`ageDays`（核验距今整数天数）、以及价格变动字段 `previousPriceFen` 与 `priceChange: { direction: 'up'|'down', deltaFen }`（仅当存在上一次核验且价格有差额时输出；首次核验或价格持平不输出）。`previousPriceFen`/`priceChange` 只由平台自有的结构化价格历史派生，不暴露来源链接或审核备注。

创建投稿后，服务端同时返回短期上传令牌；图片接口必须校验投稿 ID 与该令牌的绑定关系。查询码不能作为图片上传令牌使用。

后台列表接口统一使用 `page`、`pageSize` 分页，默认每页 50 条、最多 100 条。公开地图接口不使用普通分页，但最多返回 500 个点位。

### 10.2 管理接口

| 方法与路径 | 用途 |
|---|---|
| `POST /api/v1/admin/session` | 管理员登录 |
| `DELETE /api/v1/admin/session` | 退出 |
| `GET/POST/PATCH /api/v1/admin/leads` | 线索维护 |
| `GET/POST/PATCH /api/v1/admin/places` | 地点维护 |
| `POST /api/v1/admin/places/:id/merge` | 合并重复地点 |
| `POST/PATCH /api/v1/admin/menu-items` | 餐食维护 |
| `POST/PATCH /api/v1/admin/price-reports` | 价格维护 |
| `GET/PATCH /api/v1/admin/submissions` | 投稿审核 |
| `POST /api/v1/admin/imports/preview` | 预览 CSV 校验结果 |
| `POST /api/v1/admin/imports/commit` | 确认导入 |
| `GET /api/v1/admin/exports/full` | 导出完整备份 |

### 10.3 错误格式

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "提交内容不完整",
    "fieldErrors": {
      "price": "价格必须大于 0"
    }
  }
}
```

用户端只显示可理解的信息；服务器日志不记录密码、会话令牌、完整查询码和图片内容。

## 11. 技术架构

### 11.1 总体架构

```text
手机/桌面浏览器
       │
       ├── 高德地图 JS API（底图、交互、导航链接）
       │
       ▼
Next.js 模块化单体
  ├── 用户端页面
  ├── 管理后台页面
  ├── Route Handlers / API
  ├── 领域服务与校验规则
  ├── 数据仓储层
  └── 图片处理
       │
       ├── SQLite 数据库文件
       └── 本地受控图片目录
```

### 11.2 技术选型

| 层次 | 选型 | 原因 |
|---|---|---|
| 应用框架 | Next.js App Router + TypeScript | 一个仓库同时完成前端、后台和 API，减少 AI 上下文切换与部署单元 |
| UI | 原生 CSS + React 语义组件 | 保持票据式视觉、响应式与无障碍实现可直接审查，不引入大型设计系统 |
| 地图 | 高德地图 JS API 2.0 | 国内地图和 GCJ-02 坐标适配；通过 `MapAdapter` 隔离供应商 |
| 数据库 | SQLite | 本地零成本、备份简单，足够支撑受控 MVP |
| 数据访问 | `better-sqlite3` + SQL 仓储层 + 版本化迁移脚本 | 保持 SQL 可审查，避免 ORM 隐藏关键查询，并为迁移 PostgreSQL 留边界 |
| 校验 | Zod | 前后端共享输入校验和类型 |
| 图片处理 | Sharp | 转 WebP、缩放、移除元数据 |
| 单元测试 | Vitest | 测试领域规则和查询逻辑 |
| 端到端测试 | Playwright | 覆盖地图降级、筛选、投稿和后台审核主链路 |
| 代码质量 | ESLint + Prettier + TypeScript strict | 提前发现 AI 生成代码中的类型和风格问题 |

不在文档中锁死具体小版本。初始化项目时由 AI 选择当时稳定版本并写入 lockfile；之后未经专门升级任务不得随意改变主要依赖版本。

### 11.3 模块边界

```text
app/              页面、loading/error 边界与 Route Handlers
components/       用户端、地图与后台交互组件
lib/server/       数据仓储、领域服务、认证、校验与媒体处理
lib/              公共类型、CSV、地理与地图适配
db/migrations/    SQLite 版本化迁移
scripts/          初始化、备份、恢复、维护与隔离验收
tests/            领域和接口测试
e2e/              Playwright 主流程
```

页面和 API 不直接写 SQL；所有读写经过模块服务和仓储层。模块之间通过显式函数调用，不引入消息队列。

### 11.4 地图适配层

定义统一 `MapAdapter` 接口，业务页面不得直接散落高德 SDK 调用。至少包含：

- 初始化和销毁地图
- 设置中心与缩放级别
- 读取当前视野边界
- 渲染、更新和清除标记
- 点击标记事件
- 用户定位
- 打开导航

提供两个实现：

1. `AmapAdapter`：真实高德地图。
2. `DemoMapAdapter`：无需密钥的测试替身，用于自动化测试和密钥尚未配置时的开发。

高德 Key 可以出现在浏览器配置中，但安全密钥必须通过服务端代理或官方推荐的安全方式使用，不得提交到 Git 仓库。

浏览器定位通常提供 WGS-84 坐标，而高德地图使用 GCJ-02。定位点进入地图和距离计算前必须经过一个集中封装的坐标转换函数；数据库只存 GCJ-02，并在字段注释、导入模板和 API 文档中明确坐标系。禁止在页面组件中散落转换逻辑。

- 执行数据库迁移。
- 导入不含版权风险的演示数据。
- 提示高德 Key 未配置时将使用 DemoMapAdapter。

`npm run maintenance` 用于执行被拒投稿、仅后台图片、分析事件和日志的保留策略；没有定时任务的 MVP 由后台提示管理员按需执行。

### 12.2 备份

备份输出为单个 ZIP 文件，命名为 `budget-map-backup-YYYYMMDD-HHmmss.zip`，应包含：

- SQLite 数据库一致性快照
- 平台自行上传的图片
- JSON 或 CSV 格式的关键数据导出
- 备份清单和生成时间

`manifest.json` 必须记录 schema 版本、应用版本、文件清单和 SHA-256 校验值。

恢复使用 `npm run restore -- --from <备份文件>`。脚本必须先执行只读校验，确认 ZIP 结构、校验值和 schema 兼容性；随后自动备份当前数据，在临时目录完成恢复和完整性检查，最后原子替换。任何步骤失败都保留原数据。恢复属于有数据覆盖风险的操作，必须要求操作者输入明确确认词，且必须有文档和自动化测试。禁止只依赖某台电脑上的未备份数据库文件。

### 12.3 受控测试部署

本地验收通过后，再单独选择临时部署方式。部署不是首轮编码的前置条件。候选方式必须满足：

- 支持常驻 Node.js 进程和持久化磁盘；
- 可以配置 HTTPS、环境变量和备份；
- 中国大陆访问基本可用；
- 不要求立即拥有自有域名；
- 可在成本或政策不合适时迁移。

不将 SQLite 部署到无持久化文件系统的 serverless 函数中。

### 12.4 正式化迁移条件

出现以下任一情况时，评估迁移至 PostgreSQL、对象存储和正式域名：

- 公开地点超过 5,000 个；
- 多人同时运营后台；
- 图片量或备份体积明显增长；
- 需要微信小程序；
- 需要多个城市和更复杂的空间查询；
- 受控测试证明产品有稳定复访和投稿。

迁移后数据库采用 PostgreSQL + PostGIS，图片迁移至国内对象存储。业务层和 API 契约保持不变。

## 13. 安全、隐私与内容治理

### 13.1 管理员安全

- 管理员密码不写入代码或数据库明文。
- 使用强密码哈希和带签名、HttpOnly、SameSite 的会话 Cookie。
- 管理接口统一鉴权；用户端无法访问来源链接和审核备注。
- `npm run admin:password` 负责交互式生成密码哈希并提示写入本地环境变量，不修改源代码。
- 管理会话默认 8 小时失效；修改密码后旧会话全部失效。
- 同一来源 15 分钟内最多失败登录 5 次，超过后锁定 15 分钟。
- 所有管理写操作校验 Origin 并使用 CSRF token；登录状态错误统一返回 401/403，不泄露内部原因。

### 13.2 投稿安全

- 所有输入在服务端二次校验和长度限制。
- 图片只允许 JPEG、PNG、WebP，单张原图不超过 10 MB，每次投稿最多 5 张；同时校验 MIME 和实际文件签名。
- 图片重新编码后保存，不直接保存用户上传的原文件。
- 处理后图片最长边不超过 1600px，并去除 EXIF。
- 同一来源每小时最多提交 5 次、查询状态 10 次。仅使用每日轮换盐值生成的来源哈希进行限流，不保存原始 IP。
- 设置蜜罐字段，并限制正文、店名和地址长度。
- 不允许提交 HTML，不渲染富文本。
- 图片只有在投稿者完成权利确认、管理员完成人工隐私检查并将 `visibility` 设置为 `public` 后才可公开；否则仅后台可见。

### 13.3 隐私最小化

MVP 不收集姓名、手机号、微信身份或精确轨迹。浏览器定位仅用于当前页面计算距离，默认不写入数据库。服务器日志不保存精确位置参数的长期用户画像。

被拒绝投稿在 90 天后执行内容清理事务：先删除只关联该投稿、且未关联正式价格的媒体文件与媒体行，再将 `payload_json` 替换为只含投稿类型和清理标记的最小墓碑记录；保留投稿 ID、状态、创建/审核时间和已脱敏审核原因用于审计。清理失败必须整体回滚数据库变更并保留原文件。原始分析事件和应用日志保留 30 天；管理员审计记录和已公开事实历史长期保留，直到产品停止或另行制定删除政策。

### 13.4 内容治理

- 所有用户内容先审后发。
- 提供纠错和下架入口。
- 后台保留审核记录，公开端不显示外部平台用户身份。
- 对商户使用客观事实描述，避免未经证实的贬损性评价。

## 14. 数据导入模板

CSV 导入采用“预览—纠错—确认”两阶段，不允许直接写库。下载模板向产品负责人显示中文列名，导入时统一转换为内部字段；旧英文模板继续兼容。不得改变列名或顺序。

| 中文列名 | 内部字段 |
| --- | --- |
| 片区名称 | `zone_name` |
| 店铺名称 | `place_name` |
| 地址 | `address` |
| 经度 / 纬度 | `lng` / `lat` |
| 坐标系 | `coordinate_system` |
| 店铺类别 | `place_category` |
| 准入类型 | `access_type` |
| 餐食名称 | `menu_item_name` |
| 餐食类别 | `menu_category` |
| 价格（元） | `price_yuan` |
| 核验日期 | `observed_date` |
| 核验方式 | `verification_method` |
| 证据文件名 | `evidence_filename` |
| 线索链接 | `source_lead_url` |
| 后台备注 | `admin_note` |

“坐标系”是必填列，MVP 唯一允许值为 `GCJ-02`。浏览器 CSV 导入不读取操作者电脑上的任意本地路径。“证据文件名”只允许留空；若非空则整批拒绝。阶段 3 已实现投稿与管理员受控图片上传，但没有把证据文件并入 CSV 批量导入。

导入校验必须发现：

- 必填项缺失
- 非法价格和日期
- 坐标超出初始可配置范围（GCJ-02：经度 113.6～114.7、纬度 22.4～22.9）；MVP 作为硬错误拒绝，避免误导入外省坐标
- `coordinate_system` 缺失或不是 `GCJ-02`
- 重复来源链接
- 疑似重复地点
- 不允许的核验方式
- `evidence_filename` 非空（证据图片必须走受控上传链路）

来源链接和管理员备注只进入后台，不得被公开 API 返回。

## 15. 分析指标

首版不引入复杂第三方分析 SDK。数据库已预留 `analytics_events`，但阶段 5 首轮采用主持人匿名观察表，不接入用户行为事件写入。若后续改成无人主持或远程测试，再单独确认是否以匿名、最小化的服务端事件表记录：

- `map_viewed`
- `filter_changed`
- `place_opened`
- `navigation_clicked`
- `submission_started`
- `submission_completed`

不得记录完整 IP、精确移动轨迹或能够拼接成个人画像的标识。受控测试阶段的核心指标：

1. 10～30 名目标用户完成真实试用。
2. 至少 30～50 份可信餐食可用。
3. 用户能够在 30 秒左右找到符合预算的餐食。
4. 地点详情到导航点击存在实际转化。
5. 用户能理解“核验日期”和“待核验/已核验”的差异。
6. 至少出现少量自然纠错或新线索提交。

这些指标用于判断是否继续投入，不作为对外宣传数据。

“30 秒找餐”采用任务测试衡量：至少 10 名目标用户从地图首页开始，执行“在指定样板区找到一份不超过 20 元的餐食并说明如何前往”；至少 8 人在 30 秒内完成，且没有把待核验或超过 180 天的价格误认为当前有效价格。未达到时先修正信息架构和文案，不扩大功能范围。

## 17. 测试策略

### 17.1 单元测试重点

- 价格以分存储和展示。
- 最新有效价格选择。
- 90/180 天新鲜度计算。
- 收录价格门槛。
- 地点重复候选规则。
- 公开 DTO 不泄露后台字段。
- 投稿状态转换。
- CSV 字段与坐标校验。

### 17.2 集成测试重点

- 地图视野和筛选查询。
- 一个投稿从创建到批准的完整事务。
- 地点合并后餐食、价格和证据的归属。
- CSV 预览和确认导入的一致性。
- 备份和恢复。

### 17.3 端到端主流程

1. 用户打开地图，选择 20 元以内，查看地点并点击导航。
2. 用户拒绝定位，仍能从默认样板区开始浏览。
3. 用户提交一个涨价纠错，得到查询码。
4. 管理员登录、审核纠错并登记新价格。
5. 用户端显示新价格和核验日期，旧价格仍保留在历史中。
6. 管理员导入 CSV，先看到错误预览，修正后成功导入。
7. 无地图密钥时自动切换测试地图且不阻塞其他功能。

## 18. AI 执行规则

### 18.1 单一事实来源

- 本文档定义产品和架构边界。
- `docs/DECISIONS.md` 记录实施过程中批准的变更。
- `docs/PROGRESS.md` 记录完成项、验证结果和未解决问题。
- 不允许只在对话里改变重要规则而不更新文档。

### 18.2 每个开发任务必须包含

- 目标和不做什么。
- 允许修改的文件或模块。
- 输入输出或接口契约。
- 验收标准。
- 必须运行的检查。
- 已知风险与回滚方式。

### 18.3 Token 与复杂度控制

- 一次只实现一个可验收纵向切片。
- 优先复用浏览器、框架和 SQLite 能力，不自研基础设施。
- 不因“未来可能需要”增加微服务、缓存、队列或账号系统。
- UI 和业务逻辑分离，避免一次修改牵动所有页面。
- 依赖必须有明确用途；能用少量代码完成的能力不引入大型依赖。
- 每阶段结束后整理进度文档，下一阶段只加载必要上下文。

### 18.4 变更控制

以下变化必须回到产品负责人确认：

- 扩大试点区域或新增城市。
- 改变 25 元核心收录门槛。
- 开放用户内容免审发布。
- 引入登录、支付、广告或商业合作。
- 改用自动抓取外部平台数据。
- 增加需要持续付费的云服务。
- 更换地图或持久化技术并造成数据迁移。

## 19. 风险与停止条件

| 风险 | 早期信号 | 处理方式 |
|---|---|---|
| 可信数据不足 | 30～50 份都难以核验 | 暂停公开产品开发，先验证采集方法 |
| 豆瓣线索过旧 | 大量店铺涨价或停业 | 降低豆瓣线索优先级，寻找近期来源和现场共建者 |
| 单人审核负担过重 | 待审核持续积压 | 缩小区域、限制投稿入口，不增加复杂自动审核 |
| 地图供应商配置受阻 | 无法申请或安全配置 Key | 保留 DemoMapAdapter，重新评估腾讯地图等替代方案 |
| 用户只看不贡献 | 有浏览但无纠错/投稿 | 先优化提交成本和提示，再决定是否做共建者机制 |
| 用户无法理解可信度 | 把过期或待核验当成事实 | 强化状态文案，必要时隐藏待核验信息 |
| 维护成本超过收益 | 个人无法持续更新 | 停止扩区，复盘是否存在稳定共建者和真实复访 |

出现以下情况时，应停止扩展而不是继续增加功能：

- 无法合法、持续地获得足够线索和核验数据。
- 目标用户并不使用地图完成就餐决策。
